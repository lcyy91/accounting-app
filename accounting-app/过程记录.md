## 一、需求分析与 AI 对话记录

### 1.1 第一次对话：提出核心需求

> **日期：** 2026-05-04  ·  **方式：** 自然语言描述

**用户输入（Prompt）：**

> 做一款记账的软件

**AI 理解与分析：**

AI 收到需求后，将其拆解为以下关键问题：

1. 用户是个人记账场景，不是企业财务系统
2. 需要方便快捷的记录收支
3. 需要有数据统计和可视化
4. 数据必须持久保存，不能刷新就丢失

**AI 规划的功能模块：**

| 优先级 | 模块 | 说明 |
|:---:|------|------|
| P0 | 交易增删改查 | 核心记账功能，必须实现 |
| P0 | 数据存储 | 用浏览器 localStorage 持久化 |
| P1 | 月度筛选 | 按月查看收支情况 |
| P1 | 统计仪表盘 | 收入、支出、结余一目了然 |
| P2 | 图表可视化 | 饼图 + 柱状图展示数据 |
| P2 | 分类管理 | 预设常用分类，支持选择 |
| P3 | 数据导入导出 | 备份和迁移数据 |
| P3 | 响应式设计 | 手机也能用 |

## 三、调试日志与问题解决

### 问题 1：API 服务端连续返回错误

| 项目 | 内容 |
|------|------|
| **时间** | 2026-05-04 21:47 ~ 22:12 |
| **严重程度** | 🔴 高（阻塞开发流程） |
| **影响范围** | 导致 AI 无法正常返回响应 |

**错误现象：**

连续多次收到以下两种错误：

```
401 Unauthorized
（认证失败）
```

```
400 Server error (target: https://api.deepseek.com)
（请求被服务端拒绝）
```

**排查步骤：**

| 步骤 | 操作 | 结论 |
|:---:|------|------|
| 1 | 重新发送相同请求 | 仍然 401，不是偶发问题 |
| 2 | 检查错误码变化（401 → 400） | 排除权限问题，是服务端处理异常 |
| 3 | 假设响应体过大导致拒绝 | 将大型回复拆分为多次小请求 |
| 4 | 验证分步请求策略 | ✅ 分步后请求正常通过 |

**最终解决方案：**

将原来的大步长开发流程改为**分步任务模式**：

- 每个操作（写文件 / 创建任务 / 读取文件）独立发送
- 使用 Task 系统追踪进度
- 避免单次响应包含过多内容

**经验总结：** 在使用 AI 辅助开发时，将任务拆解为小步骤不仅能提高成功率，也让开发过程更清晰可追溯。

## 四、架构设计思路

### 整体架构

```
┌──────────────────────────────────────┐
│              浏览器                   │
│  ┌────────────┐  ┌────────────────┐  │
│  │  index.html │  │  Chart.js CDN  │  │
│  │  (单文件)   │  │  (图表库)       │  │
│  └─────┬──────┘  └────────────────┘  │
│        │                              │
│  ┌─────▼──────┐                       │
│  │localStorage │  ← 数据持久化        │
│  │  (浏览器DB) │                       │
│  └────────────┘                       │
└──────────────────────────────────────┘
```

### 设计原则

1. **零依赖安装** — 纯浏览器原生技术，双击即用
2. **数据本地化** — 数据归用户所有，无需注册账号
3. **渐进增强** — 先保证核心功能可用，再叠加辅助功能

## 五、技术选型与设计决策

### 5.1 为什么选择纯 HTML 单文件架构？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **纯 HTML 单文件（✅ 采用）** | 双击打开、零配置、老师可直接预览 | 代码组织不如分文件清晰 |
| React / Vue 框架 | 组件化开发、生态丰富 | 需要 Node.js、构建工具，非专业学生上手困难 |
| Python + Flask | 后端能力强 | 需要安装 Python、命令行启动，过于复杂 |

**决策理由：** 对于非计算机专业学生，**可用性 > 技术先进性**。老师拿到仓库链接后能直接在线看运行效果，比下载一堆环境再配置强得多。

### 5.2 为什么选择 localStorage？

| 方案 | 适用场景 |
|------|----------|
| **localStorage（✅ 采用）** | 个人记账，数据量小，无需共享 |
| IndexedDB | 数据量大（>5MB），结构复杂 |
| 后端数据库（MySQL等） | 多用户系统，需要服务器 |

**决策理由：** localStorage 容量约 5MB，一条记账记录约 200 字节，理论上可存 25000+ 条记录，完全够用。配合导入导出功能弥补了无法跨设备自动同步的短板。

### 5.3 配色方案

遵循**中国金融市场习惯**（与美国相反）：

| 元素 | 颜色 | 色值 | 含义 |
|------|------|------|------|
| 收入 | 🔴 红色 | `#e17055` | 涨 = 红色（中国习惯） |
| 支出 | 🟢 绿色 | `#00b894` | 跌 = 绿色（中国习惯） |
| 主色调 | 🟣 紫色 | `#6c5ce7` | 现代、稳重、中性 |

### 5.4 分类设计

参考了日常个人财务管理中最常见的场景：

- **支出：** 覆盖"衣食住行 + 精神消费 + 应急"，共 9 类
- **收入：** 覆盖"主动收入 + 被动收入"，共 5 类
- 预留「💡 其他」作为兜底分类
